# Suno 6.0 · 문법 2트랙 다양화 — 기획 v0

**발주**: LEO 09-10 직지시 — 「수노가 6.0 엔진으로 바뀌어서 **기존 우리 방식으로도 되고, 더욱 자연스러운 자연어 방식도 된다**. 우리 레오뮤직OS 문법도. **2가지로 다양화하는 걸 기획**해야겠다」
**이 문서의 지위**: 기획(설계)만. **생성 0 · 크레딧 0**. 실행분은 §5에서 LEO 승인 항목으로 갈라 둔다.

## §1. ⛔기저 실측 3건 — 기획 전에 세어 본 것

1. **★코퍼스에 판본 칸이 없다.** `data/reanalysis_v2/merged_4values.json` 560레코드 전수 — 키는 `song_id·title·genre·subgenre·bpm·key_signature·leomusic_original{sp,lyrics}·suno_reanalysis`뿐이고 **`model`·`version`·`created` 문자열 등장 0건**(09-10 실측). `sunolang.db`도 같다(`tracks`에 판본 칸 없음, `match_runs.corpus_version`은 우리 코퍼스 판번호이지 엔진 판본이 아니다).
   ⇒ **우리는 지금 6.0 관측을 받아도 구판 관측과 한 통에 섞는다.** 사전이 조용히 오염된다.
2. **Suno엔 seed가 없다**(통제면 대장 §2 — seed 보유 7엔진에 Suno 미포함). 같은 입력을 두 번 넣어도 고정 재현이 안 된다.
3. **take 산포가 조건차보다 클 수 있다** — 같은 가사·같은 SP인데 곡 길이 폭 **19.0 / 28.5 / 18.9 / 36.4초**(상대 7.8~16.8%, `scripts/vd_take_spread_v1.py`). ⇒ **T-S vs T-N을 각 1 take로 비교하면 그 차이는 잡음에 묻힌다.**

## §2. 2트랙 정의 — 무엇과 무엇을 가르는가

| | **T-S 구조화 트랙**(현행) | **T-N 자연어 트랙**(신설) |
|---|---|---|
| SP 칸 | 악기·질감·믹스 서술자 나열형(≤1,000자 관행) | 한 사람이 설명하듯 이어지는 산문 |
| 가사 칸 | 섹션 대괄호 + 지시 대괄호/소괄호 큐 | 지시 최소화 — 필요한 것만 문장으로 |
| leomusic OS 문법 | **입력 규격**으로 직행(현재 위치) | ★**중간표현으로 후퇴**시키고 렌더 직전 자연어로 펼침 |
| 강점(가설) | 재현·검수 가능, 게이트로 하드검증 가능 | 6.0이 문맥을 읽는다면 의도 전달이 더 정확할 수 있음 |
| 약점(가설) | 모델이 안 받는 파라미터가 텍스트로 샘(D015 계열 가설) | **검수 자동화가 어렵다** — 문장은 grep으로 못 가른다 |

★**핵심은 「어느 쪽이 좋은가」가 아니다.** 두 트랙은 **다른 실패 양식**을 갖는다 ⇒ 곡·요건별로 **고를 수 있게** 만드는 것이 이 기획의 산출이다.

## §3. 이 기획이 답해야 하는 질문 3개

- **Q1 회귀** — 6.0에서 **T-S가 여전히 유효한가.** 우리 대장의 D축 값들이 판본 넘어 살아남는가(특히 대괄호 큐 반영률·소괄호 거동). ⚠R2가 이미 외부 E4로 「v4.5→v5에서 소괄호 거동이 변했다」를 잡았다 — **판본 간 변화는 이미 관측된 축**이다.
- **Q2 이득·손실** — T-N이 무엇을 더 얻고(의도 정확도?) 무엇을 잃는가(**검수 가능성**·재현성).
- **Q3 충돌** — 둘을 섞으면 충돌하는가. 우리 D012·D037·D046(필드충돌)과 LeVo 공식 경고(`descriptions`↔`prompt_audio` 충돌 시 instruction following 저하)가 같은 방향을 가리킨다.

## §4. 단계 (P0가 전제 — 건너뛰면 나머지가 오염된다)

- **P0 판본 칸 신설** *(생성 0 · 지금 할 수 있음)*
  ⑴입력 표본 등록부·코퍼스 레코드에 `suno_engine_version` 칸 신설 ⑵**소급 판정 가능성 조사** — 기존 560곡의 판본을 사후에 알 수 있는가(생성 원장·uuid·날짜 경유). ⛔알 수 없는 건 **`unknown`으로 적는다**(추정 금지) ⑶사전 v3.6 스키마에 판본 축 반영 여부 판단.
- **P1 T-N 문법 초안** *(생성 0)* — 사전 437원자 중 **자연어로 펼칠 층**과 **그대로 둘 층**을 가른다. leomusic OS 문법 → 자연어 변환 규칙표 v0(antisuno `portability_rules_v0.md`의 T0~T4 등급을 그대로 재사용 — 이미 「무엇이 엔진 중립 정본인가」를 정의해 둔 자산이다).
- **P2 사전등록 A/B** *(★생성 필요 = LEO 승인 항목)* — 같은 곡·같은 의도를 T-S / T-N으로. **seed 없음 + take 산포**를 고려해 조건당 take 수를 §1-③ 수치로 산정하고 **재기 전에 등록**한다. 종속변수는 **자동 판정 가능한 것부터**(브라켓 누출·요건 적중·길이) — 청음 판정은 LEO 트랙을 쓰므로 마지막에.
- **P3 사전 분기** — 결과에 따라 사전을 **트랙별 층**으로 가른다(v3.5의 입력층 분리와 같은 형태). ⛔통합하지 않는다 — 층이 다른 값을 한 칸에 넣는 것이 v3.4에서 이미 낸 사고다.

## §5. LEO 결정이 필요한 것 3개

1. **6.0 접근 경로** — 어느 계정·어느 파이프라인으로 6.0을 쓰는가(sunomusic 생성 레그가 6.0을 쓰고 있는가). ⇒ P0의 소급 판정 가능 여부가 여기서 갈린다.
2. **leomusic OS 문법의 위치** — 입력 규격으로 유지할 것인가, **중간표현으로 후퇴**시키고 트랙별로 펼칠 것인가. *(제 권고 = 후자. 그래야 T-S·T-N이 같은 원본에서 나온 두 표현이 되고, 비교가 성립한다.)*
3. **P2 생성 예산** — 조건당 take 수 × 곡 수. 산정치는 P1 끝에 숫자로 올린다.
